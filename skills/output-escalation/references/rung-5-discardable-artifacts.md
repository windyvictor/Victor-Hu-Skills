# R5 — 可丢弃软件件（Discardable Artifacts）

Karpathy 原话："as intelligence and code are increasingly abundant, you can ask for large,
custom, **discardable** software artifacts (e.g. web apps, video explainers) that would have
never made sense to create before. Push the boundaries here."

这是整个阶梯的**世界观**，不只是第五级。它的意思是：**软件工程的成本约束已经变了。**

---

## 1. 核心判断

过去：写一个只给三个人用一周的小工具不划算。立项、评审、维护，成本远超收益。
所以大家改用"口头解释 + Excel 凑合"。

现在：**产出成本 → 接近零**。于是出现了一类新东西：

> **用完即弃的定制软件件**——为**这一件事、这一批人、这一周**而做，做完就可以删。

这类东西的判据不是"能不能长期维护"，而是"**能不能把这件事讲清楚/做快**"。

## 2. 什么时候升到 R5

命中任一，就考虑要一个"件"而不是一次"答"：

- **重复性**：这件事每周都要做一次（→ 做成脚本/工具）。
- **参数化**：每次只是换几个输入（→ 做成带表单的小应用）。
- **需要试错**：使用者要试探不同假设（→ 做成模拟器）。
- **需要协作**：多人要对着同一个东西讨论（→ 做成一个可分享的页面）。
- **需要留痕**：要保留每次的输入输出（→ 做成带本地存储的记录器）。

## 3. 形态选择

| 需求 | 形态 | 备注 |
|---|---|---|
| 一次性计算/转换 | 单文件脚本（`.py`/`.sh`/`.js`） | 最快，命令行即可 |
| 需要调参数反复用 | 单文件 HTML 工具（无后端） | 双击即用，可分享 |
| 需要交互 + 保存 | HTML + `localStorage` | 仍无后端，数据留在本机 |
| 需要多端同步/协作 | 带后端的 Web 应用 | 成本上一个台阶，想清楚再上 |
| 需要接外部数据 | 脚本 + API 调用 | 注意密钥不要写进文件 |

**默认最小实现**：单文件、无构建、无后端、无依赖安装。能用 200 行解决的不要写 2000 行。

## 4. 最小实现约定

1. **一个文件、一个动作**。文件名叫得清用途（`palleting_cost_calc.html`）。
2. **零配置运行**：双击就能开，或一行命令就能跑。需要装依赖的，在文件头写成注释。
3. **输入有默认值**：打开就能看到结果，不要空表单。
4. **输出可直接复制**：结果区有复制按钮，或纯文本可选中。
5. **失败要吵**：出错就明确报错，不要静默返回 0 或空。
6. **不写入用户目录**：需要落盘就写当前工作目录。
7. **可以删**：不注册服务、不装后台进程、不改系统配置。

## 5. 边界与纪律

- **不要用"可丢弃"当借口降低质量**：能被看懂的数据才算对，能被用的界面才算完成。
- **不要在可丢弃件里放密钥**。要用 API 就从环境变量读。
- **不要把可丢弃件当产品交付**：如果它活过了三个月，就要回头补文档和边界。
- **用完就删**：这是这一类东西的尊严所在。留在磁盘上的半成品比删掉更糟。
- **判断升级**：从 R3 网页 → R5 工具的唯一差别是"**会被反复使用**"。如果只讲一次，别升。

## 6. 与阶梯的关系

R5 不是终点，是**态度**。往回看：

- 每一级的正当理由都是"减少读者的力气"，不是"增加产出的体量"。
- 阶梯往上走，**成本往上涨、读者的力气往下降**。找到性价比最高那一级就停。
- 默认姿态：能一句话说清就一句话；需要被看清就给图；需要被试探就给网页；
  需要被看完就给视频；需要被反复用就给工具。**然后继续往上推——试过才知道边界在哪。**
